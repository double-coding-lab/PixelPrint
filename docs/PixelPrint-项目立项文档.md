## 一、项目背景

### 1.1 前端还原设计稿是一项高频、重复、耗时的机械劳动


以一个中等复杂度的活动落地页为例——比如首页 banner 换新、大促入口、优惠券领取——从「设计稿走查完」到「视觉验收通过」的实际链路是这样的:

| 环节 | 前端要做的事 | 典型耗时 |
| --- | --- | --- |
| 读图层 | 打开 Figma,点每个图层看层级、量距离、扒颜色、复制字号 | 1~2h |
| 切图 | 挑出该切成图片的元素(icon / 装饰 / 复杂渐变),一张张导出,命名、放目录 | 1~2h |
| 撸布局 | 手写 Flex 容器、决定哪里 Auto Layout 哪里绝对定位、对齐 gap 和 padding | 3~5h |
| 写样式 | 逐行敲颜色 / 字号 / 圆角 / 阴影,对着 Figma 反复来回切 | 2~4h |
| 视觉走查 | 设计师截图标注红线,前端逐点调,来回 2~3 轮 | 2~4h |

一个中等页面耗时 1~3 个工作日,其中 60% 以上的工时属于纯机械的「视觉抄写」——不涉及业务判断、不涉及架构决策、也不产生可复用资产。这部分工作有三个特点:

- 对业务侧,是必要但难以压缩的开发成本,页面越多累计越显著
- 对开发侧,长期从事这类工作缺乏成长,团队内部普遍缺乏投入意愿
- 对团队侧,直接占用前端产能,挤压真正需要架构判断的工作

设计稿到代码之间缺乏可靠的机械翻译通道,只能靠人工逐行还原,这是 D2C 这个方向长期没被真正解决的核心原因。

### 1.2 直接把设计稿丢给 AI 模型,产出什么样

在没有规则约束的情况下,AI 直接处理设计稿常见的产出问题有以下四类:

**一、遇到复杂结构直接切成整块图片**

AI 处理不了复杂结构(嵌套 Auto Layout、渐变叠加阴影、多层滚动区)时,倾向于把整块切成 PNG。产物看起来还原度很高,但内部结构完全丢失:

```jsx
<div style={{ backgroundImage: `url('banner.png')`, width: 375, height: 240 }}>
  <div style={{ position: 'absolute', top: 180, left: 120, width: 100, height: 40 }}
       onClick={handleClick} />  {/* 透明点击区 */}
</div>
```

导致的后果:

- 文案无法动态修改
- 换语言 / 换主题时需要重新导出整张图
- 无障碍能力完全丢失
- 后续接埋点、A/B 测试、SSR 都无法支持

**二、布局全部使用绝对定位堆叠**

AI 拿到 Figma 节点的 `x/y/width/height` 后,常见做法是照抄坐标:

```jsx
<div style={{ position: 'relative', width: 375, height: 812 }}>
  <div style={{ position: 'absolute', top: 120, left: 24, width: 327, height: 44 }}>
    <span style={{ position: 'absolute', top: 12, left: 16 }}>标题</span>
  </div>
  <div style={{ position: 'absolute', top: 180, left: 24 }}>...</div>
</div>
```

外观上像素对齐,但:

- 修改任何一个字段可能导致整块布局塌陷
- 无法响应式适配,375 一改就崩
- 无法接入现有 Flex / Grid 组件库,需要整体重写
- 可读性差,后续维护成本高

这种代码在真实业务的 code review 环节会被直接打回。

**三、遇到不确定的属性凭感觉生成**

设计稿里的渐变、阴影、padding 等属性,AI 如果没被强制读取 Figma 原始节点,会生成"看起来差不多的值":

- padding 是 16px,查 Figma 原稿实际是 24px
- 渐变颜色写作 `#FF6B00 → #FFA24C`,Figma 里实际是 `#FE6600 → #FFAA50`
- 字号写了 14px,Figma 里是 15px

单个错误不致命,但一个页面几十个节点、每个节点 3~5 个属性,累计误差足以让设计走查无法一次通过。

**四、遇到麻烦时声称已完成、实际未做**

最难识别的一种问题是 AI"装完成"——它自己也没意识到在偷懒:

- 让它切图,写了占位符 `<img src="TODO.png" />` 就继续往下走
- 让它对齐样式,写了空 `style={{}}` 声称"样式已应用"
- 让它检查 data-node-id 覆盖率,跳过校验直接输出"校验通过"

如果规则里预留了「实在不行,人工核对」这条路径,AI 会把大量本可以机械算出的属性推到"待人工核对",因为对它来说标记 TODO 比算对一个数字容易得多。

### 1.3 为什么 AI 会这样——缺少配套的工程约束

上述四类问题,根因不是模型能力不足,而是缺少一份能被 AI 直接执行的、覆盖「D2C 该怎么做、什么绝对不能做、边界如何校验」的工程规则包。

当前业界现状:

- 业务方自己写 skill:主要靠几十行 prompt 提示词,遇到复杂稿容易失败,且难以定位问题
- 求助开源方案:大多停留在 demo 级别,缺少经过真实业务场景反复打磨的规则积累
- 归因于模型能力:实际情况是,AI 拿到清晰的规则约束时表现差异显著,问题主要在缺少配套约束

AI 层面缺失的是三样配套:能执行的规则、规范化的输入、机械校验的兜底门禁。三者配合,才能让 AI 在真实业务场景下产出可上线的代码。

PixelPrint 提供的正是这三件东西:

- 一套让 AI 按工程规范翻译设计稿的约束体系,每条规则对应过真实事故、每条门禁都拦过具体错误、每个前缀都经过实战验证
- 一份设计师侧的图层协作规范,保证 AI 拿到的输入本身就是清晰、可解析的
- 一套跑在 AI 出码前后两端的机械校验层(`check-rules.mjs` 逐节点对账),减少模型出错余地

已在内外双仓发布:内仓 `@ctrip/pixel-print`(公司内部 npm registry)+ 外仓 `@double-coding/pixel-print`(公网 npm + GitHub 开源),覆盖 H5 侧(pp-d2c)与 RN 侧(pp-d2c-rn,可通过 adapter 映射到 xtaro / taro 等 RN-like 框架),规则完全可见可改。

## 二、公司内部现有方案的问题

公司内部已有若干团队尝试过 D2C 方案,基于我们的观察,普遍存在以下缺陷:

**问题一:图层输出错误**

- 切图区域计算不准(常见:未处理 `useAbsoluteBounds`,导致渐变 / 阴影被裁掉)
- 相同图片重复导出,包体积膨胀
- 复杂图层降级成"整块切图",丢失可维护性(文字变图片、按钮变图片)

**问题二:大量使用绝对定位堆布局**

内部方案普遍产出的代码形态类似:

```jsx
<div style={{ position: 'absolute', top: 120, left: 24, width: 327, height: 44 }}>
  <span style={{ position: 'absolute', top: 8, left: 12 }}>标题</span>
</div>
```

这种输出的问题是:表面还原度尚可,但可维护性差:

- 内容长度一变化,整块布局崩掉
- 响应式适配无从谈起(不能自适应父容器)
- 无法接入现有 Flex / Grid 组件库
- 修改一个字段可能需要重新计算全屏坐标

**问题三:缺失设计侧协作规范**

D2C 效果的天花板受设计稿本身质量约束,这一点在实践中经常被低估。设计稿如果没有清晰的图层组织、命名规范、组件抽取,AI 拿到的输入就是一堆没有语义的矩形,模型能力再强也难以翻译出合理的代码结构。

内部现有方案在这一环上普遍缺失,导致上游输入不受控:

- 设计师随意起图层名(`Rectangle 42` / `Frame 128`)
- 该抽 Auto Layout 的地方用绝对定位摆
- 该切图的元素与该保留为 DOM 的元素混在一起
- 相同的模块每次都重画,不复用组件

上游输入不规范,下游 AI 再强也无法产出规范代码。PixelPrint 与内部现有方案的一个核心差异,是把设计侧协作作为方案的第一环节,提供一份可直接下发给设计师的规范文档(`PixelPrint-设计师图层规范.md`)。


### 与 PixelPrint 的对比

| 维度 | 内部方案 A(某前端平台) | 内部方案 B(某业务线自研) | **PixelPrint** |
| --- | --- | --- | --- |
| 布局方式 | 大量绝对定位堆叠 | 大量绝对定位堆叠 | **优先 Auto Layout / Flex,绝对定位仅作退路** |
| 切图问题 | 部分区域切错 / 重复导 | 部分场景整块切图 | **前置切图 + imageRef 去重 + 4 道图片对账门禁** |
| 图层规范 | 无 | 无 | **`PixelPrint-设计师图层规范.md` 完整规范,设计师侧协作** |
| 图层命名要求 | 无强要求 | 无强要求 | **前缀协议 `sub-/img-/bg-/btn-/fixed-/list-/bl-` 等 12 类语义标签** |
| 校验机制 | 无 | 无 | **`check-rules.mjs` 硬防线 + Rule-Scan 软防线** |
| 跨端支持 | 单端 | 多端 | **H5 侧 + RN 侧 两套 SKILL,RN 侧可通过 adapter 映射到 xtaro / taro 等 RN-like 框架** |
| 使用形态 | 平台化,黑盒 | 内部工具,难扩展 | **本地 AI Agent 直接调用,零平台依赖** |

**核心差异**:内部现有方案的问题主要在两处——设计侧缺少规范化输入约束、出码后缺少机械校验兜底。AI 的概率性输出需要两层确定性代码在前后夹持,否则难以稳定产出可上线代码。PixelPrint 的整体架构就是围绕这两道防线设计的。

### 差异化定位小结

PixelPrint 补齐了内部现有方案缺失的两道确定性防线:

- **上游**:图层前缀协议 + `PixelPrint-设计师图层规范.md` 设计侧规范,把 AI 拿到的输入约束在可解析范围内
- **下游**:`check-rules.mjs` 17 条硬规则 + 4 道门禁,以 cache 为真值逐节点对账

在这两道防线的夹持下,LLM 的概率性输出被限制在可上线代码的产出边界内。

### 小结

公司内部现有 D2C 方案的共同缺陷,指向同一个空缺:目前没有一套工程质量对齐业务上线标准、覆盖设计侧协作规范与出码后机械校验的 D2C 方案。这是 PixelPrint 的立项机会。

## 三、项目价值

### 3.1 直接价值:压缩「视觉还原」的工程成本

以中等复杂度的 H5 落地页为例:

| 环节 | 传统方式 | PixelPrint 方式 |
| --- | --- | --- |
| 图层拆解 | 前端手工看图分析结构 | Skill 自动读 Figma REST API,按前缀协议识别语义 |
| 切图 | 前端一张张导 | 一键前置切图(step 2.6),自动 dedupe |
| 布局撰写 | 手写 Flex / 绝对定位 | 主 agent 派 sub-agent 并行出码,遵循 Auto Layout 语义 |
| 视觉对齐 | 肉眼比对反复微调 | 内置 17 条硬规则 + 4 道门禁,机械对账 Figma cache |
| 图片压缩 | 手工过一遍 tinypng | 内置 `pp-image-compress` skill |

实测效果:单一业务线内已完成 6~10 个页面接入,D2C 耗时从 1~3 个工作日下降到 0.5~1.5 小时,前端开发从视觉抄写工作转向业务逻辑与架构工作。

### 3.2 间接价值:输出标准化的设计-前端协作规范

设计师按 `PixelPrint-设计师图层规范.md` 组织图层,前端才能拿到高质量输入。这份规范本身可作为团队级资产沉淀——即便未来不用 PixelPrint,规范化的设计交付也能为其他 D2C 方案提供更好的输入。

### 3.3 战略价值:布局 AI Coding Agent 生态

Claude Code / Codex 等 AI Coding Agent 生态正在快速形成 skill 这种可复用能力包机制。PixelPrint 面向该生态提供设计稿到前端代码方向的能力包,内仓 `@ctrip/pixel-print` 服务公司内部前端团队,外仓 `@double-coding/pixel-print` 在公网 npm 与 GitHub 开源,具备以下延伸空间:

- 沉淀公司在 AI Coding Agent 生态方向的技术积累
- 服务公司内部前端工程效率
- 具备对外输出为公开工具的条件,可作为技术输出物

### 3.4 已有实测效果

H5 侧已在**火车票增长业务线**内 6~10 个页面完成实测,数据如下:

| 指标 | 传统方式 | PixelPrint 方式 |
| --- | --- | --- |
| 中等复杂度活动页 D2C 耗时 | 1~3 个工作日 | 0.5~1.5 小时 |
| 效率提升 | — | **约 5~20 倍**(视稿件复杂度而定) |
| 视觉还原度 | 设计走查通常 2~3 轮 | 一次走查通过占多数 |
| 代码可维护性 | 手写质量参差,常见绝对定位堆叠 | Flex / Auto Layout 为主,统一走前缀协议 |

**当前局限**:实测数据来自单一业务线(火车票增长),且仅覆盖 H5 侧。**跨业务线接入验证是 P1 阶段的核心工作**——需覆盖不同稿件风格、不同技术栈的团队,回收量化数据后立项文档更新为 v1.1。RN 侧目前处于产品化早期,尚未大规模实测,同步纳入 P1 试点范围。

## 四、技术方案(概要)

### 4.1 三层架构:两个确定层夹一个概率层

```
┌─────────────────────────────────────────────────┐
│ 🟦 数据层  figma.mjs                             │
│   Figma REST API · 切图 · cache · truncation 检测 │
└─────────────────────────────────────────────────┘
                     ↓ (确定性数据)
┌─────────────────────────────────────────────────┐
│ 🟧 执行层  LLM Agent(Claude Code / Codex)       │
│   读规则 → 派 sub-agent → 出 JSX/SCSS → 自检     │
└─────────────────────────────────────────────────┘
                     ↓ (概率性产出)
┌─────────────────────────────────────────────────┐
│ 🟦 校验层  check-rules.mjs                       │
│   17 硬规则 · 4 道门禁 · 以 cache 为真值逐节点对账 │
└─────────────────────────────────────────────────┘
```

**核心原则**:允许兜底的路径就是错误来源。所有能从设计稿机械算出的东西,禁止 LLM 用「待核对」兜底。

### 4.2 关键机制

- **前缀协议**:12 类语义化图层标签(`sub-/img-/bg-/bgc-/btn-/input-/scrollx-/scrolly-/fixed-/end-/bl-/list-` 等),把设计师的命名转成 agent 可读的语义结构。
- **Sub-agent 分块并行**:主 agent 按 `sub-*` 前缀拆块,派多个 sub-agent 并行出码,合并前逐块 `check-rules --block` 门禁,合并后 `check-rules --merge` 二次对账。
- **以 cache 为真值的逐节点对账**:所有校验直接读 `.d2c-cache/` 里的 Figma 原始节点 JSON,独立于 LLM 的自我声明。
- **软 / 硬双防线**:硬防线 17 条 exit-1 硬规则 + 4 门禁(cache 完整性 / 规则命中 / 图片对账 / 切图确认);软防线 5 条语义类规则由 Rule-Scan sub-agent 出作业指引。
- **Adapter 机制**:通过 config 里三张表(`tagMap` / `importMap` / `propMap`)把 RN 内核标签映射到任意 RN-like 框架,一份 skill 覆盖多端。

### 4.3 已交付版本能力矩阵

| 侧 | SKILL | 版本 | 关键能力 |
| --- | --- | --- | --- |
| **H5 侧** | pp-d2c | v1.2.7 | 17 硬规则 + 4 门禁 + 前置切图 + 图层前缀协议(含 bl-/list-)+ 目录三态守卫 |
| **RN 侧** | pp-d2c-rn | v1.1.2 | RN 内核六件套 + adapter 机制(可映射到 xtaro / taro 等 RN-like 框架)+ 22 硬规则(含 RN 特有 RN01-04)+ styleMatch 引擎 |

- 🎯 与内部 UI 组件库深度对接

## 六、风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 设计师不愿改图层规范 | D2C 效果打折 | `PixelPrint-设计师图层规范.md` 已尽量降低学习成本(15~20 分钟);提供设计师侧收益说明(减少返稿) |
| Figma REST API 变更 | 数据层可能失效 | 数据层已隔离在 `figma.mjs`,变更影响面可控;跟进 Figma 官方 changelog |
| AI Coding Agent 侧接口变化 | Skill 可能需要重写 | SKILL.md 是纯自然语言操作手册,兼容多 agent(已同时支持 Claude Code / Codex);变化时以规则文件为真值,agent 侧只需换壳 |
| 复杂业务场景仍需人工兜底 | 无法完全自动化 | 定位为「工程加速器」而非「完全替代前端」,人工兜底是设计上定义清晰的路径,而非黑盒 |
| 内部推广阻力 | 试点难以扩大 | 先以自愿接入为主,量化数据积累到足够说服力后推动更广接入 |

## 七、结论

PixelPrint 面向的问题是:在 AI Coding Agent 能力已具备的前提下,如何用工程手段约束模型,产出符合业务上线标准的 D2C 代码。

方案的核心是一套双确定性架构——数据层 + 校验层两个确定层夹持 LLM 这一概率层,配合设计侧协作规范,把设计稿到前端代码这一高频重复环节的产出质量提升到可直接合入业务代码库的标准。

当前 H5 侧 SKILL 已完成产品化(pp-d2c v1.2.7)、RN 侧 SKILL 已完成产品化(pp-d2c-rn v1.1.2),内外双仓 1.5.0-beta 已发布,并在火车票增长业务线内 6~10 个页面完成实测(D2C 耗时从传统 1~3 个工作日下降到 0.5~1.5 小时,效率提升约 5~20 倍)。申请立项支持,推动跨业务线试点扩展与量化数据积累,进入下一阶段。
